# StormOps v3.0.0 — Local Operations, Failure Safety and Observability

**Maintainer:** Samuel Texa
**License:** MIT
**Runtime:** Java 21 bytecode, tested on Java 21 and Java 25
**Release scope:** Isolated local-first chaos engineering laboratory

## Highlights

V3 builds on the V2 secure experiment lifecycle. It improves reproducible
published-image testing, operator tooling, failure-mode confidence and
read-only operational evidence. These improvements do not turn StormOps into a
production fault-injection service.

- **Published image end-to-end evidence:** immutable GHCR images are exercised
  in a uniquely created kind cluster, with explicit recovery assertions.
- **Secure local operator CLI:** diagnostics and application launchers validate
  runner credentials, loopback targeting, permissions and private files.
- **Operational failure regressions:** durable run reservations and
  `INJECTION_INTENT` survive database outages, child-JVM crashes and TCP
  partitions without retrying Kubernetes operations.
- **Backup and restore:** disposable PostgreSQL source/destination containers
  verify restored experiment history, Flyway migrations, audit sequence and
  fail-closed safety state.
- **Operational observability:** a secured, read-only status endpoint combines
  persistent safety state with the existing Prometheus precheck assessment.
  This is evidence for inspection, not execution authorization.
- **CI validation:** Java 21/25 unit and PostgreSQL integration tests,
  frontend validation, image smoke tests and scoped disposable-kind proof.

## Upgrade considerations

Both the API and demonstration-service Maven versions advance to `3.0.0`.
No database migration is introduced solely for this release. Existing Flyway
migrations and the V2 persistent reservation remain in effect.

Before running the new binary, independently back up the local database,
keep authentication enabled, validate the runner ServiceAccount permissions,
inspect the safety stop/active reservation and confirm the allowed laboratory
cluster. Never reset an ambiguous `active_run` during an upgrade.

The operator tools do not provision credentials, deploy a new cluster, or
run a destructive experiment on startup. Any real fault still requires
explicit operator review, prerequisites and confirmation.

## Verification and scope

Review the main [CI and image delivery guide](../CI_DELIVERY.md), the
[V3 failure testing matrix](../V3_OPERATIONAL_FAILURE_TESTING.md),
[operational recovery evidence](../V3_RECOVERY_EVIDENCE.md) and
[V3 observability contract](../V3_OPERATIONAL_OBSERVABILITY.md).

A passing isolated regression suite does not prove multi-host linearizability,
production disaster recovery, guaranteed uptime or full Kubernetes outage
reconstruction. The monitoring UI is unchanged in V3. Runtime images remain
Linux amd64; release publication and immutable digests are recorded separately
only when the `v3.0.0` tag workflow succeeds.
